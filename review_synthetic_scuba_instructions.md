> **Status (2026-10-26):** The fixes below have been folded into `claude_code_instructions_synthetic_scuba.md`. Two items depend on access rather than text: A3 (reading the metadata catalogue) and the CmdStan download in A2. The instructions now tell the run how to proceed without them.

> **Network update (2026-10-26, later the same day):** A recheck found that GitHub release downloads now work, so CmdStan can be installed, and that the public catalogue repository can be cloned, although its content is a PDF rather than a schema file. CRAN still serves source packages only, because Posit Package Manager and r2u are blocked. Project Euclid and the CIMIS sites remain blocked, and the Docker daemon is still not running. This review flags issues in the synthetic SCUBA instructions before the first run. Issues are grouped by severity. The first group should be resolved before the run, because each one will either stop the run, cause a validation gate to fail, or force the agent to make a large judgment call silently. Section numbers refer to the instructions file.

## A. Resolve before running

**A1. The panel is 76 months long, not 72.** January 2010 through April 2016 contains 76 monthly bills, but section 2 calls it 72 months and section 7 computes 216,000 account-months from that figure. The April 2016 end date is the one to keep, because rebates posted as late as April 2015 need 12 post-rebate months, which only fit if the panel runs through April 2016. The fix is to change "72 months" to "76 months" in both places and the account-month count to about 228,000.

**A2. The R path works now, but CmdStan still cannot be installed.** R is not preinstalled in this container, but Ubuntu's archive offers `r-base-core` 4.3.3 through apt. After the network policy update, both `https://cloud.r-project.org` and `https://cran.r-project.org` answer, so `install.packages()` and `renv::restore()` will work. GitHub release downloads still return 403, and that is where both `cmdstanr::install_cmdstan()` and `cmdstanpy.install_cmdstan()` fetch CmdStan. The simplest workaround is to use `brms` with `backend = "rstan"`, because `rstan` installs from CRAN and compiles models with the system g++. Section 6's "pin the CmdStan version" would then become "pin the rstan and StanHeaders versions." The other option is to allow `github.com` and `objects.githubusercontent.com` in the network policy. Some CRAN packages also need system libraries (for example `arrow`, `sf`, `curl` and `xml2`), and those come from apt, which works. The Docker binary is present, but the Docker daemon is not running, so the Dockerfile can be written but not built or tested here. The Project Euclid paper URL and the CIMIS site are also blocked, so the agent cannot consult the paper or calibrate ET0 to CIMIS during the run.

**A3. The metadata catalogue could not be read from this session.** The instructions tell the agent to mirror the SCUBA catalogue's field names, but the session's GitHub access covers only this repository, and my request to attach `California-Data-Collaborative/metadata_catalogue` was not approved. Without it, the agent will guess field names such as `usage_et_amount_default`, `cust_loc_id` and `location_id_from_utility` from the text of the instructions alone. Either grant read access to that repository for the run, or paste the relevant schema files into this repository before starting.

**A4. The winter savings target conflicts with the physical feasibility constraint.** Section 4 computes outdoor demand from net ET (ET0 minus effective rainfall, floored at zero) and forbids savings larger than the untreated outdoor demand. With the section 3 tables and even 50 percent rainfall effectiveness, net ET in January is about 0.2 inches for Anytown California and zero for Valley Small Town. In Anytown, a 4,000 square foot landscape then needs only about 500 gallons of outdoor water in January, while a 1,000 square foot turf removal at the target 1.5 gal/sqft/month implies 1,500 gallons of savings. The cap will bind across much of the cohort from December through February, which will pull the January-to-March mean well below 1.5 and fail the gate in stage 4. Real households overwater in winter because irrigation timers ignore rain, so the cleanest fix is an explicit behavioral irrigation term, for example applied water equal to the larger of the agronomic need and a fixed fraction of ET0, times a household overwatering factor. Lower rainfall effectiveness alone would also help but would weaken the coastal-versus-inland contrast.

**A5. The treated share will not reach 150 to 200 after the filters.** Assuming about 85 percent of the 3,000 accounts are single family, a 6 to 8 percent selection rate yields roughly 150 to 205 treated households before any filtering. The instructions then remove households through late rebates that fail the 12-month post filter, duplicate rebates, defaulted irrigable area, missing data and possibly turnover, which together could remove 20 to 30 percent of them. The result would be roughly 110 to 160 households in the analysis cohort, which fails the stage 6 gate. Either raise the selection target to about 9 to 11 percent, or state the target as the post-filter count and let the generator calibrate the selection intercept to hit it.

**A6. The tiny profile cannot pass the stage 6 gate.** The tiny profile has 500 accounts across 12 zip codes, which is about 40 accounts per zip code, while the gate requires at least 100 control candidates per zip code. The tiny profile also assigns 100 accounts to every retailer, which departs from the default proportions. The instructions should say whether tiny uses one zip code per retailer, whether gates scale with the profile, or whether tiny is exempt from the cohort-size gates.

**A7. The size of each turf removal is never specified.** Rebate square footage drives the savings per square foot, the area ratio covariate in the savings regression, the $2 per square foot payment and the feasibility cap, yet no distribution is given for it. The agent needs an assumed distribution, for example a lognormal with a median near 1,000 to 1,500 square feet, a floor at a program minimum such as 250 square feet, and a cap at a fraction of the irrigable area. All of these values should be tagged `assumed` unless the paper reports them.

## B. Clarify to avoid silent judgment calls

**B1. The 3,000-account target is ambiguous once new construction and closures exist.** New construction adds about 1 percent of accounts per year and closures remove a few, so the count differs at the start and end of the panel. The instructions should say whether 3,000 is the count in January 2010, the count in April 2016, or the number of locations ever observed.

**B2. Account-level year built is used but never defined.** Irrigable area has an inverse link to year built, but only block group median year built is specified, and it is bounded between 1940 and 2010. New construction during the panel needs a year built of 2010 or later, which falls outside that bound. The instructions should add an account-level year built drawn around the block group median, with new construction exempt from the upper bound and given smaller turf areas consistent with California's landscape ordinance.

**B3. The usage model covers only single family homes.** The indoor formula uses household size, which does not apply to commercial, institutional or irrigation accounts, and multi-family accounts need a unit count. The class shares are also unspecified. Section 2 lists seven DWR classes, but section 2's follow-on paragraph names only five of them, leaving out industrial and other. A short class-specific demand model and a share for each class would close this gap.

**B4. The drought effect has no magnitude.** Section 4 specifies a common drought effect starting in April 2015, but it gives no size, and the stage 3 gate asks only for "a visible 2015 drop." California's urban suppliers reduced use by roughly 24 percent against 2013 under the 2015 mandate, which suggests an assumed single family effect of about 20 to 25 percent. The supplier report's "percent reduction relative to 2013" will otherwise come out near zero during 2014, so a smaller voluntary effect from early 2014 would also be worth adding. Note that the executive order came on April 1, 2015, and the State Water Board's mandatory reductions took effect in June 2015. The April date can stay because it matches the paper, but the README should note the distinction.

**B5. Bimonthly billing is not carried through to the analysis.** The instructions do not say how the 24-month and 12-month filters, the BSTS fits and the efficiency variable should handle the two bimonthly retailers. They also do not say whether bimonthly read dates are staggered across billing cycles or aligned to calendar months. The efficiency variable adds 1 to both use and budget, so its value depends on whether it is computed per bimonthly period or per month, and the unit (CCF per billing period is the natural choice) should be stated.

**B6. Turnover after a rebate needs a rule for the savings effect.** The removed turf stays with the property, but the instructions do not say whether the household savings random effect persists with the property or is redrawn with the new occupant. That choice changes the true savings stored in the truth folder.

**B7. The other rebate types need a stated effect.** High efficiency clothes washer and weather based irrigation controller rebates are generated, but the instructions do not say whether they reduce usage, whether those accounts count as treated, or whether they may serve as controls. If they reduce usage, they contaminate the control pool, so the effect should be specified and stored in the truth folder.

**B8. Matching with or without replacement is unstated.** With about 15 to 20 treated households per zip code and 6 controls each, matching without replacement uses 90 to 120 controls from a pool of roughly 170 to 230 single family accounts, which is tight once filters apply. Matching with replacement avoids the problem but should be stated.

**B9. The supplier reconciliation needs a loss factor and a number.** Supplier production exceeds retail sales because of non-revenue water, which typically runs 5 to 10 percent. The generator needs an assumed loss factor, an assumed service population for each retailer, the acre-foot to gallon conversion in the GPCD formula, and a numeric reconciliation tolerance.

**B10. The gates need numeric thresholds.** Words such as "mostly," "plausible" and "visible" leave the agent to grade its own work. Examples of concrete thresholds are at least 90 percent of single family account-months between 0 and 100 CCF, at least 80 percent of annual totals between 100 and 600 CCF, an inland July-to-January ratio greater than every coastal ratio, and a 2015 drop within a stated range.

## C. Compute, reproducibility and structure

**C1. The Stan validation steps are expensive and loosely specified.** The generator is nonlinear, because indoor and outdoor demand add before a lognormal error is applied, and it carries a household AR(1) state. A brms model cannot express that structure directly, so "refit the generating model's multilevel structure" needs to name the model, such as a model of log usage with the structural mean as an offset, and the list of recovered parameters. A 500-account fit over 76 months has about 38,000 observations plus latent AR(1) states, and simulation-based calibration repeats a smaller fit at least 100 times. On this four-core container, those steps could take many hours, and a cloud session can be reclaimed during idle periods. Both should sit behind flags, like the causal recovery step, with a stated runtime budget.

**C2. Position-indexed RNG streams are not truly keyed to unit IDs.** `parallel::nextRNGStream()` produces streams by position, so adding a retailer or switching profiles shifts every later stream. A more robust scheme derives each stream from the root seed, a stage identifier and a hash of the unit ID (for example `SeedSequence([root, stage_id, hash(unit_id)])` in Python). Separate substreams per stage keep the usage draws unchanged when a later stage such as turnover is modified. Draws shared across units, such as year anomalies, retailer-by-month shocks and the drought effect, also need their own named streams.

**C3. The memory rules add complexity without benefit.** The default panel has about 228,000 rows and the large profile has about 912,000, and both fit in memory many times over on this 15 GB machine. Chunking by retailer and avoiding loading the potential-outcomes table will add code paths without saving anything meaningful, so I would drop that requirement or apply it only above some row count.

**C4. The script numbering does not map to the build stages.** Section 9 asks for scripts `01` through `08` plus `09_validate`, while section 5 has seven stages. A one-line mapping from script to stage would help, and the `R/` folder name should change (for example to `src/`) if the Python fallback is used.

## D. Minor notes

**D1.** The ET0 annual totals check out against the stated values (47.2, 55.1, 48.6, 59.3 and 55.7 inches). Anytown California is described as moderate and near the coast, but its July-to-January ratio of 3.9 is larger than So Cal Suburb's 3.0 and close to Inland Enclave's 4.0. That may be intended, but it blurs the coastal-versus-inland contrast the gates check.

**D2.** The instructions say "water years 2012 to 2015" without defining a water year. The California convention runs from October through September, which should be stated.

**D3.** Vacant homes often keep irrigating because timers keep running, so "near-zero usage" during vacancy may understate real vacancy rows. This is a modeling choice worth logging rather than a defect.

**D4.** The Parquet determinism rules are achievable with pyarrow if the index is not written and the library version is pinned, since the `created_by` string is fixed by the lockfile.

**D5.** Many observation-layer rates are left open, including the missing-row rate, the share of defaulted irrigable area, the duplicate-rebate share and the erroneous-value share. Section 10 already tells the agent to choose and log defaults, so this is fine, but the user may want to set them in advance.

**D6.** The paper's numbers (the 545 households, the seasonal savings, the Figure 3 spread and the Table 3 signs) could not be checked against the paper itself because the publisher's site is blocked from this session. They should be spot-checked by someone with the paper at hand.

## E. Note added 2026-10-26: why the tail targets moved and why "true" became "planted"

The first build placed the paper's savings targets (the mean, seasonal means, median, quartiles and tail shares) on the effect the generator plants. That was a category error. The paper's figures are estimates from matched households and Bayesian structural time series, so they include estimation error, and noise widens a distribution. A planted distribution tuned to match the paper's estimated tails would therefore be too wide, and the tuning itself chased one-household misses in a cohort of about 200. The paper's bands now apply to the matched difference-in-differences estimates computed from the synthetic data. The planted effect only has to meet looser, assumed tolerances, and its level and spread are chosen by a bounded anchor calibration so that the estimates reproduce the paper's estimated moments. Tail shares are judged by a binomial rule, and stage 4 is judged by its pass rate across 20 seeds.

The word "true" has been replaced by "planted" for the same reason. Nobody knows the savings of real households, because their counterfactual usage is never observed. The synthetic generator knows each household's savings only because we wrote the data-generating process, so the stored quantity is an assumption we planted and not knowledge about the world. The validation now asks whether matched difference-in-differences recovers an effect we planted, and how robust that recovery is when the planted world changes, rather than whether it recovers the truth.
