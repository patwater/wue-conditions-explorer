# Synthetic SCUBA and Turf Rebate Data: Instructions for Claude Code

## 1. Goal and deliverables

Build a reproducible generator for fully synthetic water utility data that mirrors the schema of the California Data Collaborative SCUBA metadata catalogue and the structure of the California Turf Rebate Dataset (CTRD) described in Schmitt, Tull and Atwater (2018), "Extending Bayesian structural time-series estimates of causal impact to many-household conservation initiatives," Annals of Applied Statistics 12(4), 2517-2539. The paper is available at https://projecteuclid.org/journalArticle/Download?urlId=10.1214%2F18-AOAS1166 and the catalogue is at https://github.com/California-Data-Collaborative/metadata_catalogue. Both documents are the source of the bounds in this specification. The data must carry the effect of turf removal that the generator plants in every treated household, so that analysts can test how well a savings estimator recovers a known, planted answer.

Savings are estimated with statistical matching and difference-in-differences (matched DiD) in the spirit of the paper, and the paper's Bayesian structural time series pipeline (called M123 in the paper) is kept as an optional comparison. Nobody knows the true savings of real households, because their counterfactual usage is never observed. The generator knows each synthetic household's savings only because we wrote the data-generating process, so every stored effect is a planted assumption and not a fact about the world, and every column, table, figure and heading must say "planted" rather than "true". The validation therefore answers a narrower question than whether the method recovers the truth. It asks whether matched DiD recovers an effect we planted, in a world with turnover, vacancy, missing rows, drought shocks and selection on conservation attitude, and how robust that recovery is when the planted world changes.

The deliverables are a config file holding every parameter, a numbered set of generation scripts, the output tables, a truth folder, a validation report, an environment record, and a README that documents the data-generating process. Use R as the default language because the CaDC tools (RateParser, OWRS) are written in R. In the Claude Code cloud environment, install R from the Ubuntu archive with apt (`r-base-core`, `r-base-dev`, and system libraries such as `libcurl4-openssl-dev`, `libssl-dev` and `libxml2-dev` as packages require them), and install R packages from CRAN at https://cloud.r-project.org. CRAN serves source packages only in this environment, because the binary repositories (Posit Package Manager and r2u) are blocked, so expect long compile times for `rstan` and `brms` and set `MAKEFLAGS` to use all cores while installing. Use `fixest`, `metafor` and `sandwich` for the matched difference-in-differences estimation. Use `brms` with `backend = "rstan"` for the refit checks, because `rstan` installs from CRAN, compiles with the system g++, and is locked by `renv` like any other package. GitHub release downloads now work in the environment as of October 2026, so `cmdstanr` with a downloaded CmdStan is an acceptable alternative if `rstan` proves too slow. If R cannot be installed, use Python with numpy, pandas, pyarrow and PyMC (all available from PyPI), and say so in the README.

Read the metadata catalogue before writing the data dictionary, and use its field names exactly. The catalogue is a public repository that can be cloned from the environment, and its content is a PDF (`metadata_catalogue.pdf`), so extract the field names and definitions from the PDF text and record the commit hash that was read. If the catalogue cannot be read, use the field names given in this document, mark every field name that was inferred rather than read in the data dictionary, and list them in the README so the user can correct them. The paper on Project Euclid and the CIMIS websites are blocked by the environment's network policy as of October 2026, so use the values in this document for the paper's figures and the ET0 tables, and say so in the README.

The first build is small: 3,000 accounts spread across 5 fictional retailers, described in section 3. The code must treat the account count, retailer list and treated cohort target as configuration, so a later run can scale up without code changes.

Everything produced is synthetic. Do not request, read or embed any real customer data. Do not use real utility names, real street addresses or real assessor parcel numbers. Use only the five fictional retailer names given in section 3, and add a column `is_synthetic = TRUE` to every table, plus a banner at the top of the README stating that the data is simulated and must not be mistaken for real records.

## 2. How to treat the source documents as bounds

Every parameter in `config/params.yaml` must carry a `source` tag with one of three values: `catalogue` (taken from the SCUBA metadata catalogue), `paper` (taken from the AOAS paper), or `assumed` (chosen by you because the sources are silent). Keep a short `rationale` string beside each assumed value. Where a value is assumed, prefer widely cited physical or demographic reasoning and mark it so the user can overrule it. The table below lists the bounds the generated data must respect.

The paper's savings figures are estimates that carry estimation error, so they anchor the estimated side of the results and not the planted effect directly. The sign pattern of Table 3 anchors the direction of the planted savings regression, while its magnitudes remain assumed. The planted effect only has to respect looser, assumed tolerances, and its level and spread are then chosen by the anchor calibration in section 4 so that the matched DiD estimates reproduce the paper's estimated moments.

Most accounts receive potable water. About 30 percent of irrigation accounts receive recycled water, and a handful of irrigation and industrial accounts in Valley Small Town receive raw water.

## 4. The generative model

State the model in the README before writing code, as Gelman and Hill recommend, and keep the code a literal translation of that statement. The model is multilevel and generates potential outcomes, so that both the untreated and treated usage exist for every account-month in the truth folder.

**Geography and covariates.** Create the five retailers, their zip codes and their block groups from section 3. Draw block group median household income from a lognormal distribution centered on the retailer median and bounded between $25,000 and $250,000, median year built between 1940 and 2010, and average household size between 2 and 4. Let income, year built and household size covary through a shared block group effect. Generate fake latitude and longitude from a synthetic grid for each block group and jitter accounts within it. Generate synthetic parcel identifiers that cannot resolve to real parcels.

**Accounts.** Nest accounts in block groups and assign each account a customer class using the shares in section 2. For every account, draw an account-level year built around the block group median, bounded between 1900 and 2009 for accounts that exist in January 2010. For single family accounts, draw household size from a truncated Poisson shifted to start at 1 and centered on the block group average, and draw irrigable area in square feet from a lognormal distribution centered on the retailer median (bounded between 500 and 40,000, with a positive link to income and an inverse link to account-level year built). Also draw meter size and a pressure zone. Include a latent, unobserved conservation attitude `a_i` drawn from a normal distribution with a block group mean. This latent attitude lowers baseline usage and raises the probability of taking a rebate, which creates the selection bias that the paper's time series matching is designed to handle.

**Occupancy timeline: turnover, new construction and closures.** Generate the occupancy timeline for every location before generating usage, so the usage panel is built once with the right occupants. Treat these as three distinct processes and never conflate them with missing data. Occupant turnover means a household moves out and another moves in at the same physical property. It occurs at an assumed rate of about 7 percent per year for single family homes. On turnover, keep `location_id_from_utility` and the property attributes (including irrigable area and any removed turf) fixed, assign a new `cust_id_from_utility` and a new `cust_loc_id`, insert a vacancy gap of zero to three months with present billing rows, and redraw household size and the latent attitude `a_i` (partially, to keep some correlation with the block group). During vacancy, indoor use is near zero, and outdoor use continues at a fraction drawn uniformly between 0 and 1 of the untreated outdoor demand, because some vacant homes leave irrigation timers running and others shut them off. New construction means a new property appears mid-panel with a new `location_id_from_utility`, at an assumed rate near 1 percent of accounts per year, concentrated in the So Cal Suburb and Inland Enclave retailers. New construction has a year built equal to its first billing year, which is exempt from the 2010 bound on block group medians, and its irrigable area is drawn about 30 percent smaller than older homes in the same block group to reflect California's landscape ordinance. Closure means a property demolished or merged, at a very low rate, after which its rows stop. Store the event type, date and affected IDs in the truth folder. Define pre-rebate filters and the pre-removal efficiency variable at the location level, keep a flag `turnover_in_pre_period` and a flag `turnover_in_post_period` on treated locations, and report in the validation suite how turnover affects the analysis cohort and the efficiency measure.

**Untreated monthly usage for single family accounts.** Model usage in CCF as indoor plus outdoor demand. Indoor demand equals household size times a household-specific gallons per capita day (assumed lognormal near 55) times days in the period, divided by 748.052. Outdoor demand equals 0.623 gallons per square foot per inch of applied irrigation depth, times the turf and landscape area, times a plant factor, divided by an irrigation efficiency, times a household overwatering factor `o_i` (assumed lognormal with median 1.0 and log-scale standard deviation 0.3), then divided by 748.052. The applied irrigation depth is the larger of net ET (ET0 minus effective rainfall, floored at zero) and an irrigation floor equal to 0.5 times ET0 (assumed). The floor represents irrigation timers that run in winter regardless of rain, which is common in real households and is what makes winter savings from turf removal possible. Multiply the sum by a lognormal error that combines four pieces: a household random intercept that includes `a_i`, a household-level AR(1) deviation, a retailer-by-month shock, and the common conservation effects from section 2 (a voluntary effect from February 2014 and a larger mandatory effect from April 2015). Add a slow local level and trend term that mirrors the local linear trend in the paper's BSTS model. Use varying intercepts and slopes by retailer and block group, with partial pooling and explicit hyperparameters, as in chapters 12 and 13 of Gelman and Hill. Store each account-month's structural mean (the indoor plus outdoor demand before the lognormal error) in the truth folder, because the recovery check in section 8 uses it.

**Untreated usage for other classes.** Keep these models simple, because they exist to exercise the class field and the supplier totals rather than the causal analysis. Multi-family accounts use the single family indoor formula multiplied by a unit count (assumed between 2 and 50), plus a small shared landscape area. Commercial, institutional, industrial and other accounts draw a lognormal base demand by class with a mild seasonal term proportional to ET0. Irrigation accounts use the outdoor formula alone, with irrigable areas between 5,000 and 200,000 square feet. All classes share the retailer-by-month shock and the conservation effects.

**Treatment.** Choose treated accounts with a logistic selection model in income, irrigable area, pre-period efficiency, and the latent attitude. Calibrate the selection intercept so that the post-filter analysis cohort hits the configured target (default 175, within 150 to 200), which is expected to require selecting about 9 to 11 percent of single family accounts because the filters and the observation layer remove some treated households. Draw rebate dates so that post-inspection dates fall mainly between April 2012 and April 2015, and add a smaller number of later rebates that fail the 12-month post filter. Draw the turf area removed from the distribution in section 2, and compute the area ratio as turf area removed divided by irrigable area. The planted household-level savings per square foot of turf removed follows a regression whose coefficient signs follow Table 3 of the paper: more savings for households that were inefficient before removal, a diminishing return in the log of rebate quantity and area ratio, less savings per square foot in higher income areas, more savings when ET is high, plus a seasonal cosine pair. Add a household random effect and a small share of extreme savers. Do not copy the Table 3 intercept literally, because it must be read together with covariates such as the log of median income. Planted savings begin with the first month that starts on or after the post-inspection date.

The planted distribution is chosen by indirect inference rather than copied from the paper. Because the paper's figures are estimates, and estimates add noise to whatever effect is present, the planted distribution should come out tighter than the estimated one, and the variances should roughly satisfy estimated variance = planted variance + placebo variance. The anchor calibration sets the planted level and spread with at most three knobs (`savings_target_annual_mean`, the structural skew scale and the extreme-saver share) and at most 12 candidate runs on the large profile, adjusting the mean first and the spread second. Each run is scored with a loss over the estimated moments in section 5 (mean, median, quartiles, tail shares and the seasonal ratio), every run is written to `reports/calibration_log.csv`, and the lowest-loss parameters are frozen. The frozen values are then verified on the default profile with 20 held-out seeds. No tuning is allowed after this step, and a band that the estimates still miss is documented rather than tuned away.

Enforce physical feasibility at the household level: treated usage can never fall below the household's indoor demand, and total household savings in a month can never exceed the household's untreated outdoor demand in that month. Extreme savers near 100 gal/sqft/yr are possible because their savings come from the whole landscape, including changed irrigation habits, and not only from the removed turf. Calibrate the planted intercept after applying the feasibility cap, so that the capped planted mean over the first 12 post-months lands on the configured target, and report the share of treated household-months where the cap binds.

On turnover after a rebate, the removed turf stays with the property. Split the planted savings into a structural part tied to the turf removed, which persists with the property, and a behavioral random effect, which is redrawn for the new occupant with an assumed correlation of 0.5 with the previous occupant's effect. Store both parts in the truth folder.

**Other rebate types.** Generate high efficiency clothes washer rebates for about 3 percent of single family accounts, with an assumed indoor saving of 15 gallons per household per day, and weather based irrigation controller rebates for about 3 percent, with an assumed saving of 10 percent of outdoor demand. These accounts do not count toward the treated turf cohort, and they remain eligible as controls, because real control pools contain them too. A turf household may also hold a washer or controller rebate, with the probability driven by the shared latent attitude through `attitude_coef`, and the overlap is recorded in the truth folder. Store the planted effects of these rebates in the truth folder so the validation suite can measure how much they contaminate the control pool.

**Billing.** Compute `usage_total_bill` deterministically from usage with a synthetic tiered or budget-based rate structure, including indoor and outdoor budgets (indoor budget from household size at 55 gallons per person per day, outdoor budget from ET and irrigable area). Compute the paper's pre-removal efficiency variable as the mean of log((use + 1) / (budget + 1)) over pre-period billing periods, with use and budget both in CCF per billing period, so it can be computed exactly from the observed tables. For bimonthly retailers, this means the variable is computed per bimonthly period, and the README should note that the +1 offset makes bimonthly values slightly different from monthly ones. Write the rate structure in an OWRS-compatible form if practical, so RateParser can reproduce the bills. Do not copy any real utility's rates.

**Bimonthly billing.** Generate the truth at monthly resolution for every account. For the two bimonthly retailers, assign each account to one of two billing cycles (periods starting in odd months or in even months), jitter each read date by up to five days around the cycle boundary, and aggregate the monthly truth to these billing periods by prorating days. The 24-month and 12-month filters are measured in months, which means 12 and 6 bimonthly periods. The causal analysis in section 8 runs at the billing-period frequency for bimonthly retailers rather than disaggregating to months.

**Observation layer.** Apply the data quality features of real utility data as a separate step after generating the complete, clean panel, as in chapter 25 of Gelman and Hill on missing data. Keep the clean panel in the truth folder. The observation layer should include bimonthly billing for the two bimonthly retailers (with billing period start and end dates for all retailers), missing billing rows that represent gaps in the data feed while the account stays active (these are distinct from vacancy rows, which are real), missing household size or irrigable area for some retailers, default irrigable area values that cause bunching at one value for one or two retailers (the paper drops such accounts), duplicate rebates on one account (the paper drops these), and a small share of extreme or erroneous values. Choose and record default rates for each feature in the config, tagged `assumed`.

**Rebate and supplier tables.** Write the rebate table with the catalogue's fields, including turf, high efficiency clothes washer and weather based irrigation controller types, with received date before post-inspection date before check date. Write the supplier_report table by aggregating account-level usage, scaling the sample up to an assumed service population for each retailer (recorded in the config), and adding the 7 percent non-revenue water to obtain production. Compute gallons per capita day using the catalogue's formula (current production in gallons times percent residential, divided by days in month times population served), converting acre-feet to gallons with the factor in section 2. Report a percent reduction relative to the same month of 2013 and drought-era complaints, warnings and penalties as Poisson counts that rise after mid-2014. Make the account-level and supplier-level tables consistent so that totals reconcile within 0.5 percent after the scaling and loss factors are applied.

## 5. Build order with validation gates

Work in the following order and do not move to the next stage until the gate for the current stage passes. Start with a simple model, check it, and then add complexity, which is the "start simple and meet in the middle" advice from the Bayesian Workflow paper. Every gate is a pass/fail line in the report, using the numeric thresholds below. Thresholds that refer to cohort sizes apply to the `default` and `large` profiles only, and the `tiny` profile checks proportions and skips the absolute counts. A share gate passes when its target band overlaps the 95 percent binomial interval around the observed share, with the number of treated households as n, so that a one-household miss does not fail a gate. Do not tune the generator against one-household misses on any gate.

1. Set up the repository, the environment lockfile, the config file with source tags, and the RNG scheme in section 6.
2. Generate geography, block group covariates, accounts and the occupancy timeline. Gate: plot the marginal and joint distributions by retailer, confirm that every bounded quantity falls inside its bounds, confirm that class shares are within 1 percentage point of the configured shares, and confirm that the realized single family turnover rate is between 6 and 8 percent per year.
3. Generate ET, precipitation and the untreated usage panel with no treatment and no observation noise. Gate: run a prior predictive check by drawing the parameters from their priors many times, and also check the realized panel. At least 90 percent of occupied single family account-months must fall between 0 and 100 CCF per month, and at least 80 percent of single family annual totals must fall between 100 and 600 CCF. The median ratio of July to January usage must be larger for Inland Enclave and for Valley Small Town than for Surf City. Median single family usage from June to December 2015 must be between 15 and 30 percent below the same months of 2013.
4. Add selection and treatment with the planted effects. Gate: a logistic regression of treatment on the selection covariates and the latent attitude must recover the configured coefficient signs. The planted-side tolerances are assumed and deliberately looser than the paper's bands, which move to the estimated side in stage 7. Over the first 12 post-months, the capped planted annual mean must lie between 18 and 28 gal/sqft/yr, the planted July-to-September mean between 2.0 and 3.4, and the planted January-to-March mean between 1.0 and 2.1. The planted mean must exceed the planted median, the share above 60 gal/sqft/yr must lie between 0.5 and 3.5 percent, and the share at or below zero between 0 and 8 percent, both under the binomial rule. The feasibility constraints must hold in 100 percent of account-months. A seed-robustness check reruns stages 1 to 4 on the default profile with 20 root seeds and reports every gate's pass rate, and a gate passes overall when it passes in at least 15 of the 20 seeds.
5. Add billing, the rate structure and the rebate and supplier tables. Gate: recomputing every bill from usage and the rate structure must match to the cent, and the supplier totals must reconcile with the account totals within 0.5 percent.
6. Add the observation layer. Gate: the filters must leave between 150 and 200 treated households, every zip code must have at least 100 single family control candidates, and every observation-layer feature must occur within 20 percent (relative) of its configured rate.
7. Estimate savings with matched difference-in-differences (section 8), reading only the observed tables. Gate: on the default and large profiles, the estimated turf savings must have an annual mean between 20 and 25 gal/sqft/yr, a July-to-September mean between 2.4 and 3.0, a January-to-March mean between 1.2 and 1.8, a median between 10 and 24, and an interquartile range that roughly spans 8 to 34, with tail shares judged by the binomial rule and robustness judged by the 20-seed pass rate. The absolute bias against the planted effect must stay below 3 gal/sqft/yr. The anchors come from the paper and the tolerances are assumed. Run the bounded anchor calibration in section 4 at this stage, freeze its result, and describe every remaining discrepancy in the report instead of tuning the generator to remove it.
8. Run the full validation suite in section 8 and write the report.

## 6. Reproducibility and environment

**Tiers of reproducibility.** Data generation must be byte-for-byte reproducible on any machine that uses the same lockfile. Model refits in Stan are reproducible only to numerical tolerance, because compiler versions and floating-point behavior can differ across machines, so the validation report should state tolerances and not promise identical draws. Keep the generation scripts free of Stan and of any step that depends on multithreaded floating-point reduction order.

**Random number streams keyed to stage and unit.** Derive one independent RNG stream for each combination of generation stage and unit of work, and key each stream to the stage name and the unit's ID (retailer, zip code, block group or account) and not to the position of the unit in a list or to the worker that happens to run it. This keeps results unchanged when the number of cores changes, when a profile adds or removes retailers, and when a later stage is modified. In R, compute a 32-bit integer from a hash of the root seed, stage name and unit ID (for example with `digest::digest2int()`), call `set.seed(that_integer, kind = "L'Ecuyer-CMRG")` before generating that unit's draws for that stage, and check that no two stage-unit keys produce the same integer. In Python, build `numpy.random.SeedSequence([root_seed, stage_id, *unit_words])`, where `unit_words` are 32-bit words from a SHA-256 hash of the unit ID, and create a `numpy.random.Generator` from it. Draws shared across units, such as year-level climate anomalies, retailer-by-month shocks and the conservation effects, get their own named streams in the same way. Log the root seed and the stage-unit key scheme. Never draw random numbers inside code whose order depends on scheduling.

**Deterministic outputs.** Sort every table by its keys before writing. Write Parquet with a fixed compression codec, without a row index, and without embedded timestamps or writer-version metadata that varies beyond what the lockfile fixes. Pin BLAS and OpenMP threads to one for the generation scripts. Add a test that runs the generator twice, with different core counts, and compares file hashes.

**Dependency locking.** Mandate a lockfile: `renv.lock` for R (created with `renv::snapshot()`), or `uv.lock` for Python. Pin the `brms`, `rstan` and `StanHeaders` versions (or the CmdStan version, if `cmdstanr` is used), record the C++ compiler and version, and write `reports/environment.txt` containing the R or Python version, `sessionInfo()` or `pip freeze`, the Stan toolchain versions and the compiler. Provide a `Dockerfile` built on a pinned base image tag (for example a versioned `rocker/r-ver` image) so a clean machine can reproduce the environment, and note that the container is optional for developers who already have a matching toolchain. The Docker daemon is not available in the Claude Code cloud environment, so write the Dockerfile there but state in the README that it has not been built or tested.

## 7. Compute and memory budget

The default run has 3,000 accounts over 76 months, which is about 228,000 account-months, and the large profile has about 912,000. Both fit comfortably in memory, so generate and write all tables, the clean panel and the potential outcomes for all accounts in memory without chunking. The expensive steps are model fitting, so apply these limits. Fit the multilevel recovery check on a random subsample of 500 accounts, stratified by retailer, and keep the full panel for descriptive comparisons and the replicated-data graphs. Run simulation-based calibration on the small version of the model (about 300 accounts and 36 months). Run the optional BSTS comparison on all treated households (about 150 to 200) against the same matched controls, but parallelize it across treated households using the scheme in the paper's appendix, and write intermediate results to disk so a crash does not lose progress.

Matched DiD estimation is a default step and should finish in about 10 minutes on four cores. Put the expensive checks behind flags, each off by default: `--refit` for the multilevel recovery fit, `--sbc` for simulation-based calibration, `--causal` for the BSTS (CausalImpact) comparison with the paper's method, and `--scenarios` for the scenario loop in section 8, which multiplies runtime. The default command therefore runs generation, matched DiD and the descriptive validation. The report must list which flagged checks ran and which were skipped. Aim for the recovery refit to finish within about one hour and simulation-based calibration within about three hours on a four-core machine. If a check would exceed its budget, reduce the iterations or replications, record the reduction in the report, and continue.

Provide three config profiles. The `tiny` profile has 500 accounts, with 100 per retailer and one zip code per retailer, for development. The `default` profile has 3,000 accounts across the five retailers and 12 zip codes. The `large` profile has 12,000 accounts for future use, with zip codes scaled to keep about 250 accounts each and the subsampling rules above applied automatically. Print the peak memory use in the report.

## 8. Validation suite (Gelman and Hill practices)

Write each check as a script that saves a figure and a pass/fail line to the report.

**Fake-data recovery.** Refit the multilevel error structure of the generating model to the simulated data with `brms` (on the subsample from section 7), and confirm that the generator's hyperparameters fall inside their posterior intervals at close to the nominal rate. Because the generator adds indoor and outdoor demand before applying the lognormal error, fit the log of untreated usage with the log of the stored structural mean from the truth folder as an offset. The fitted model has varying intercepts by retailer, block group and household, a household AR(1) term, retailer-by-month effects and the two conservation effects. The recovered parameters are the retailer-level and block-group-level standard deviations, the household intercept standard deviation, the AR(1) coefficient and innovation scale, and the two conservation effects. The treatment regression coefficients are checked in the causal recovery step instead. This is the fake-data simulation approach of chapter 8 of Gelman and Hill.

**Simulation-based calibration.** On the small model, repeat the simulate-and-refit cycle at least 100 times, draw parameters from the prior each time, and plot rank histograms for the key parameters. Flag any parameter whose ranks are visibly non-uniform, since that indicates a mismatch between the generator and the fitting code.

**Replicated-data comparison.** Compare the synthetic data to the documented targets using graphs rather than only summary statistics: spaghetti plots of usage by retailer, seasonal profiles that show the coastal versus inland contrast, the distribution of annual savings by year, the distribution of matched-versus-unmatched covariate distances, and residual plots. Treat these as posterior predictive style checks and describe every visible discrepancy in the report.

**Matched difference-in-differences estimation.** A separate script, `09_estimate_savings`, reads only the observed tables and never the truth folder, so it behaves like an analyst with real data, and it writes to `estimates/`. For each treated location, let R be the rebate received date and P the post-inspection date. The pre-period is every billing period ending before R, the post-period is every billing period starting on or after P, and periods overlapping R to P are dropped as the installation window. Keep single family locations with at least 24 pre-months and 12 post-months (12 and 6 billing periods for bimonthly retailers), no duplicate turf rebate and no defaulted irrigable area. The headline estimate uses the first 12 post-months and a secondary estimate uses all post-months through April 2016. A control is a single family location in the same zip code with no rebate of the type being studied, a non-defaulted irrigable area, the same billing frequency and cycle, and observed rows in at least 90 percent of the treated location's pre and post periods. Controls holding another rebate type remain eligible and are flagged in the main specification, and a sensitivity run drops them. For each treated location, compute the Pearson correlation of pre-period usage with each candidate over their common pre-period window and keep the 6 highest with replacement, breaking ties by closeness of mean pre-period usage. The `match_method` setting offers `corr_raw` (the default, closest to the paper), `corr_deseasonalized` and `corr_plus_level` (correlation plus mean pre-period usage within a factor of 2), and all three are reported in a sensitivity table, with matches written to `estimates/matches.csv`.

For each treated location, form the difference between treated usage and the mean usage of its matched controls, regress it on a calendar-month harmonic pair and a post indicator with Newey-West errors, and convert the negative of the post coefficient to gal/sqft/yr with 748.052 gallons per CCF, 12 months and the turf area removed. A second fit interacts the post indicator with the harmonic pair so the estimated seasonal profile can be compared with the planted one. A pooled stacked DiD builds one block per treated location with its 6 controls sharing the event date, divides outcomes by the treated location's turf area, weights each control by 1/6, and estimates treated-by-post with unit-by-block and period-by-block fixed effects in `fixest`, clustering by block. The household estimates are pooled with `metafor::rma`, and a meta-regression on pre-removal efficiency, log quantity, log area ratio, log income and ET is compared in sign with the planted regression. Diagnostics include an event study in 3-month bins with a pre-trend test by retailer, and a placebo test that gives each matched control a fake rebate date drawn from the treated date distribution and analyzes it exactly like a treated household. The placebo estimates should center on zero, and their spread is the noise floor of the method.

The same matching and DiD machinery is applied to the clothes washer and irrigation controller rebates, with controls that exclude any location with a turf rebate and, in the main run, any location with the other non-turf rebate. The washer estimate is converted to gallons per household per day and tested for flatness across months, and the controller estimate is converted to a seasonal effect on outdoor demand and tested for a summer peak. Both are compared with their planted effects (15 gallons per household per day and 10 percent of outdoor demand). With about 3 percent of single family accounts holding each type, only 50 to 60 households per type survive the filters, so wide intervals are an expected result and not a failure. Turf households that also hold another rebate in the analysis window carry a `cotreated_in_window` flag, and the turf results are reported with and without them. Bimonthly retailers are analyzed at the billing-period frequency and matched only within the same billing cycle.

**Comparison with the planted effect.** Over the same 12 post-months, report bias, RMSE, MAE, 90 percent interval coverage, Spearman rank correlation and the slope of the estimate on the planted effect, broken out by retailer, billing frequency, turnover in the pre-period or post-period, and the share of matched controls carrying other rebates. Compare these estimators side by side: naive pre-post without controls, unmatched DiD with all eligible controls in the zip code, matched DiD (primary), matched DiD without other-rebate controls, and BSTS if `--causal` ran. Add a log-outcome version of the DiD to show how the multiplicative drought effect interacts with a level-based estimate. Report the standard deviations of the estimated, planted and placebo distributions as a variance decomposition, which should roughly satisfy estimated variance = planted variance + placebo variance.

**Scenarios.** A `scenarios:` block in the config, tagged `assumed`, overrides the planted world while keeping the estimator fixed. The base scenario is the anchored world from the calibration. The others are differential trends (households with a stronger conservation attitude trend downward faster without a rebate, which violates parallel trends), decaying savings (planted savings fall by about half between the first and the third year after installation), concentrated savings (most households save little and a minority saves a lot), uniform savings (little heterogeneity beyond the structural regression), and high and low noise (the household usage error scaled by 1.5 and by 0.67). The scenario loop runs behind `--scenarios` and reports each estimator's bias and coverage per scenario in one table. A scenario in which matched DiD fails is a finding about which assumption the method leans on, and only the base scenario is held to the estimated-side gates.

**Edge cases.** Test accounts with short histories, rebates near the panel ends, retailers with bimonthly billing, retailers with defaulted irrigable area, vacancy gaps versus missing rows, and turnover near a rebate date, and confirm the observation layer produces them at the configured rates.

## 9. Output layout

Write the following under `synthetic_scuba/`, using Parquet for large tables and CSV for small ones, with a data dictionary that mirrors the catalogue field names.

- `config/params.yaml` and `config/profiles/`: all parameters with `source` and `rationale` fields, and the `tiny`, `default` and `large` profiles.
- `R/` (or `py/` for the Python fallback): numbered scripts that can each be run alone given the previous outputs. Use `01_geography` for retailers, zip codes, block groups and covariates (stage 2), `02_accounts` for accounts and their attributes (stage 2), `03_occupancy` for turnover, new construction and closures (stage 2), `04_climate` for ET and precipitation (stage 3), `05_usage` for the untreated panel (stage 3), `06_treatment` for selection, rebates and planted savings (stage 4), `07_billing` for rates, bills, the rebate table and the supplier table (stage 5), `08_observation` for the observation layer (stage 6), `09_estimate_savings` for matching and difference-in-differences (stage 7), and `10_validate` for the validation suite (stage 8).
- `estimates/`: the matches, household and pooled DiD estimates, meta-regression, event study, placebo results, other-rebate estimates and sensitivity tables, all computed from the observed tables only.
- `data/usage.parquet`, `data/customers.csv`, `data/rebates.csv`, `data/acs_block_groups.csv`, `data/supplier_report.csv`, `data/climate_et_precip.csv`, `data/rates_owrs/`: the observed tables using catalogue field names.
- `truth/`: quantities known to the generator, not knowledge about real households. It holds the clean panel, the structural means, the potential outcomes for every account-month, the planted household savings (split into structural and behavioral parts), the latent attitude, the planted effects of the other rebate types and their overlap with turf, the turnover, construction and closure events, and a JSON file of all generator parameters. A README in the folder states this.
- `reports/validation.html` and `reports/environment.txt`: the validation report with all figures and pass/fail lines, the planted-versus-estimated comparison, the scenario table and the seed pass rates, and the environment record. `reports/calibration_log.csv` records every anchor calibration run.
- `renv.lock` (or `uv.lock`), `Dockerfile`, and `README.md`: the lockfile, the container recipe, the synthetic data banner, the written data-generating process, the bounds tables with sources, and a limitations section.

## 10. Judgment calls to log and surface

Record each of the following in the README so the user can review them. Parameters tagged `assumed` are not supported by the sources and should be tuned by someone with real data experience, including every demographic and climate value in section 3. The paper defines pre-removal efficiency with a log ratio but describes values "below 1" as conservers, so use the log definition and treat negative values as conservers. The Table 3 intercept of about -17.7 is a model intercept rather than a standalone average and must not be used as the mean savings. The catalogue reports that the number of utilities and customer counts change over time, so keep retailer count and account counts configurable instead of hard-coded. The 3,000-account build yields fewer treated households than the paper's 545, so confidence intervals from the recovery tests will be wider than in the paper.

The following choices were added in review and should also be surfaced. The winter irrigation floor of 0.5 times ET0 is assumed, and it is what allows winter savings to reach the paper's targets without breaking the feasibility constraint. The turf area distribution, the class shares, the size of the 2014 and 2015 conservation effects, the non-revenue water share, the service populations, the effects of clothes washer and irrigation controller rebates, the vacancy irrigation fraction and the post-turnover savings correlation are all assumed. The paper dates the mandatory restrictions to April 2015, which matches the April 1, 2015 executive order, while the State Water Board's mandatory reductions took effect in June 2015. Matching with replacement is assumed, because this specification could not confirm the paper's choice. Any catalogue field names that could not be matched to the catalogue PDF are inferred. The paper's figures and the CIMIS values could not be rechecked during the run, because both sites are blocked from the environment.

The following choices were added with the switch to matched DiD and should also be surfaced. The matching details (Pearson correlation of raw pre-period usage, ties broken by mean usage, matching within billing cycle) are inferred, because the paper could not be reread. The 12-month headline window, the 90 percent coverage rule, all scenario definitions, the planted-effect tolerances and the overlap probabilities between rebate types are assumed. A level-based DiD is biased by the multiplicative drought effect, because a proportional drop in usage is larger for households that use more, which is why a log-outcome version is reported alongside it.

If any required quantity is ambiguous, choose a reasonable default, record it in the config, and continue instead of stopping to ask.

## 11. Definition of done

The work is done when the default 3,000-account run completes from a clean checkout with one command, every validation gate passes or has a documented explanation, the report lists which flagged checks ran, the report contains the planted-versus-estimated comparison, the placebo results, the other-rebate estimates, the scenario table and the seed pass rates, the truth folder reconciles with the observed tables, the README documents the data-generating process and limitations, and a second run with the same seed, on a different core count, reproduces the same data files with identical hashes.
